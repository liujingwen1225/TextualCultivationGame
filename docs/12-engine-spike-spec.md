# Engine Spike 规格：libGDX vs Godot

> 状态：待执行
>
> 目标：用一个可运行、可自动测试、范围严格受控的原型，锁定《诸世问道》的唯一桌面游戏技术栈。

## 1. Problem Statement

当前产品已经确定为 Steam / Windows 优先的东方修仙像素人生模拟 Roguelite RPG，但引擎仍有两个候选：

- Java + libGDX
- Godot + C#

单纯比较功能表无法回答本项目真正的问题：

- 一个人 + AI 能否长期高效开发；
- 地图 / UI / 动画生产是否会成为瓶颈；
- Codex 能否通过 CLI 完成构建、测试、运行、定位失败和修复；
- 核心规则是否容易保持与引擎表现层解耦。

因此必须用同一份最小玩法做技术 Spike，再做最终选择。

## 2. 固定版本

Spike 只使用稳定版本：

- libGDX `1.14.2`
- Godot `4.7.2` .NET

不使用 preview / dev 版本参与比较。

## 3. Spike 不是 V0.1 实现

Spike 只回答引擎问题，不提前建设正式游戏。

禁止在 Spike 中扩展：

- 完整黑水三世内容；
- 正式美术；
- 正式存档兼容；
- Steamworks；
- 完整战斗；
- 大地图；
- 正式 NPC 系统；
- 正式 UI 框架；
- 内容编辑器。

Spike 代码在引擎决策后允许整体删除。

## 4. 两套原型必须实现相同能力

### 4.1 一个小地图

只需要一个“青玄宗试验庭院”：

- 约 20 × 12 个逻辑 Tile；
- 墙 / 路 / 水或不可通行区域；
- 一个出生点；
- 一个 NPC；
- 一个黑水酒坛交互点。

可以使用占位几何 / 程序色块，不比较美术质量。

### 4.2 玩家移动

- WASD / 方向键移动；
- 碰撞边界有效；
- 摄像机跟随；
- 不允许像素明显抖动 / 非整数缩放导致的视觉问题；
- 移动帧数、步数不改变重大随机结果。

### 4.3 NPC / 交互

玩家靠近 NPC 后按交互键：

- 打开对话 / 事件面板；
- 展示至少两个选择；
- 事件结果由独立规则对象计算，而不是由 Scene / UI 直接修改游戏状态。

### 4.4 最小黑水规则

Spike 只保留一个足够证明解耦的规则：

```text
没有 K_BLACKWATER_POISON
→ 选择饮酒
→ Life = DEAD
→ 获得 K_BLACKWATER_POISON

已有 K_BLACKWATER_POISON
→ 事件出现“前世记忆”选择
→ 可以拒绝饮酒并存活
```

不实现完整死亡结算、承世或悟世。

### 4.5 Save / Load

至少保存：

- 玩家位置；
- Life 状态；
- Knowledge；
- 当前事件状态。

要求：

```text
保存
→ 退出运行时
→ 重新读取
→ 状态一致
```

只要求开发期格式，不要求正式兼容策略。

### 4.6 Scenario Test

两套原型都必须提供不依赖人工 UI 的场景测试：

```text
创建新状态
→ 触发酒坛事件
→ 饮酒
→ 断言死亡
→ 断言获得 K_BLACKWATER_POISON
→ 重建下一世测试状态
→ 再次触发事件
→ 断言前世记忆选项出现
→ 选择拒绝
→ 断言存活
```

## 5. 架构不变量

无论哪个候选，都必须保持：

```text
Game Core
  ↑
Application / Commands
  ↑
Scene / Input / UI
```

禁止：

- UI Button 自己决定死亡；
- Godot Node 成为 Knowledge 真值来源；
- libGDX Screen 直接修改跨世状态；
- 渲染帧率参与权威随机；
- Save 文件直接保存不可控的完整 Scene 对象图。

## 6. CLI 必须统一暴露的能力

最终命令名可以不同，但必须能被仓库顶层脚本包装成以下语义：

```text
build
unit-test
scenario-test
run
headless-smoke
```

AI 必须能够不打开 IDE 完成前四项；`headless-smoke` 必须无人工点击。

视觉 Smoke 允许依赖桌面图形环境，但也必须可由脚本启动。

## 7. 评分方式

采用 100 分加权评分，不凭主观印象直接定结论。

| 维度 | 权重 | 评价内容 |
| --- | ---: | --- |
| AI / CLI 自动化 | 20 | 构建、测试、日志、失败定位、脚本化 |
| 地图 / 场景生产 | 20 | 地图修改、碰撞、交互点、迭代成本 |
| 核心规则可测试性 | 15 | 脱离渲染测试、领域隔离成本 |
| UI / 事件表现 | 10 | 对话、事件面板、轮回类 UI 的制作成本 |
| 像素渲染质量 | 10 | 像素缩放、相机、抖动、分辨率管理 |
| 动画 / 粒子 / 光影 | 10 | 达到本项目目标所需工作量 |
| Save / 内容管线 | 5 | 本地存档和数据驱动内容难度 |
| Windows 发布 | 5 | 独立构建、运行时打包 |
| 长期维护风险 | 5 | 依赖、编辑器绑定、自研基础设施 |

## 8. 硬淘汰条件

出现任一项则候选不能直接成为正式基线：

- 不能可靠从 CLI 构建；
- Scenario Test 必须启动真实渲染窗口才能运行；
- Game Core 很难与 Scene / UI 解耦；
- AI 修改后无法通过日志或测试独立定位常见失败；
- Windows 独立构建需要不可脚本化的人工步骤；
- 一个简单地图交互就需要大量无法版本化的人工操作。

## 9. 当前假设

进入 Spike 前采用以下临时假设，不视为正式产品决策：

- 2D 俯视视角；
- 16:9 窗口；
- 键鼠优先；
- 战斗只做一次“受伤反馈”占位，不选战斗制式；
- 使用程序占位图形，不生产正式像素资产；
- 不测试 Steam SDK。

这些假设只为消除无关变量。

## 10. 决策输出

Spike 完成后必须产出：

1. 两套原型的实际运行结果；
2. 每项评分与证据；
3. AI 自动化失败点；
4. 地图 / 场景修改所需步骤对比；
5. 唯一引擎结论；
6. `docs/06-desktop-game-technical-baseline.md` 更新；
7. 必要时创建 ADR；
8. 删除失败候选或明确放入 `spike/` 历史目录；
9. 然后才进入 `to-spec → to-tickets`。

## 11. 当前预期

基于现有设计，libGDX 仍是先验优势方，因为本项目规则 / 事件复杂度高于场景复杂度。

但只有在实际 Spike 中证明：

```text
地图生产成本可接受
+
像素表现满足目标
+
AI 自动化显著顺畅
```

才正式锁定 Java + libGDX。

若 Godot 在地图、UI、动画与视觉迭代上表现出明显效率优势，且 C# Game Core 仍能保持纯领域隔离，则改选 Godot + C#。
