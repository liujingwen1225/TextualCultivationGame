# 诸世问道（暂定名）

一款以 **东方修仙 + 多世回溯 + 人生继承 + 事件驱动成长** 为核心的文字修仙 Roguelite / RPG。

> 活一世，死一次，带着记忆与选择重新走人生。

## 项目定位

玩家扮演一名普通修士，通过修炼、历练、人物关系、宗门、秘境与事件选择推进一世人生。死亡不是普通失败界面，而是核心玩法入口：系统会总结这一世，玩家选择下一世的天衍锚点，并在“承世”与“悟世”之间做一次取舍。

项目首先是一款 **游戏**。规则由代码和内容配置决定，AI 只用于人生评价、文本润色、内容生产辅助等非权威能力；V0.1 不依赖自由输入或运行时 AI。

## 核心循环

```text
新世界
  ↓
初始天衍锚点
  ↓
开始一世
  ↓
修炼 / 历练 / 社交 / 探索 / 秘境 / 决策
  ↓
条件事件 + 随机事件 + 连锁事件
  ↓
成长 / Knowledge / 功法 / 法宝 / 资源
  ↓
死亡（也允许主动坐化）
  ↓
一世评价
  ↓
选择下一世 Anchor
  ↓
承世一项成果  OR  悟世一个词条
  ↓
回溯次数 -1
  ↓
下一世
```

## 当前核心规则

### 有限回溯

- 每个新世界基础拥有 **10 次回溯**。
- 只有死亡后回溯时才消耗 1 次。
- 玩家可随时主动坐化，规则上仍然属于死亡。
- 基础次数耗尽后，可以消费账号级付费回溯额度继续；付费额度可购买且不设置总量上限。
- 若死亡时没有可用回溯次数且玩家不补充，则当前世界结束，只能开始真正的新世界。

### 多天衍锚点

- 新世界创建时自动建立初始大境界 Anchor。
- 之后 **每个大境界最多建立一个 Anchor**。
- 除初始 Anchor 外，由玩家在该大境界内自行选择时机手动“定世”。
- Anchor 建立后不可覆盖、不可更新、不会因为后续从更早 Anchor 重走人生而失效。
- 死亡后可以从所有已建立 Anchor 中任选一个作为下一世起点。

### Knowledge

Knowledge 是玩家在当前世界中真实获得的未来情报、人物秘密、地点信息、危险线索等。

- 跨 Anchor 永久保留。
- 记忆不会因世界线变化删除，但可以变成“可能变化 / 已失效 / 矛盾”。
- 真正创建新世界时全部清空。

### 承世 / 悟世

死亡结算时二选一：

**承世**：从死亡时仍合法拥有或掌握的成果中带走一项进入紧接着的下一世。

- 可承世：功法、法宝、装备、丹药、普通物品等允许成果。
- 不可承世：境界、修为。
- 高境界成果可以带回低境界 Anchor，但仍受自身使用条件限制。
- 承世只进入下一世，不是永久 Meta 背包；若以后将其固化进新 Anchor，才会成为该 Anchor 的固定状态。

**悟世**：放弃实体承世，根据这一世真实经历生成最多 3 个词条候选并选择一个。

- 词条不是抽卡，不保证每次死亡都能获得。
- 空白人生或立即自杀可能没有任何可悟词条。
- 已有同源词条可通过一次悟世升级。
- 词条库跨 Anchor 保留；每世最多同时装备 **5 个词条**。

### 唯一物

唯一物拥有世界级唯一身份，不能通过回溯复制。若唯一物被承世带离原命运轨迹，其原获取路径不会再生成第二份；如果之后既没有继续承世，也没有固化进任何 Anchor，该唯一物可能永久从当前世界消失。

### 修炼与节奏

- 修炼消耗 **游戏内时间**，不是现实挂机时间。
- 修为达到要求只是获得突破资格，突破仍可能依赖功法、状态、资源和突破事件。
- 不预设“筑基必须玩 15～30 小时”之类现实时间指标。
- 玩法节奏由有效行动、瓶颈、事件密度和重大选择控制。
- Event Pressure 主要取决于游戏时间、情境、地点、剧情压力和行动风险，不允许靠拆分点击刷事件。

### 世界与随机

正式版采用 **预设内容模块组合**，而不是运行时随机生成整个世界。

同一 Anchor 下：

- 关键人物身份、重大事件根因、重要传承等“锚点命运”相对稳定；
- 日常遭遇、普通奇遇、市场供给、部分支线等“一世变数”可以变化；
- 重大结果使用与事件上下文绑定的确定性随机，不允许通过无关操作“烧随机数”。

真正的新世界会重新组合地图、势力、NPC、秘境、事件链与核心真相，使现实玩家也无法简单照抄上一世界攻略。

## V0.1 目标

V0.1 只验证核心闭环，不追求完整产品：

```text
炼气三层 → 炼气四层
黑水场景
死亡
一世评价
承世 / 悟世
Knowledge 改变后续选择
10 次回溯
主动坐化
词条装配
确定性随机
```

V0.1 暂不把以下内容作为验收条件：多大境界 Anchor、真实支付、多世界模板、正式微信/手机号登录、小程序/App/桌面正式发布、运行时 AI 文案。

## 技术基线

```text
uni-app x + Vue 3 + TypeScript
  ├─ V0.1 主验收：Web
  ├─ 首个跨端目标：微信小程序
  └─ 后续：Android / iOS / HarmonyOS
          ↓ REST
Java 25 + Spring Boot 4.1.x
          ↓
Application / Game Core
  ├─ LiteFlow：高层流程编排
  ├─ Event Engine：事件内部规则
  └─ Deterministic Random
          ↓
PostgreSQL + MyBatis-Flex + Flyway
```

采用模块化单体优先。

正式数据访问基线为 **MyBatis-Flex**，不再使用 jOOQ。普通 CRUD / 查询优先使用 BaseMapper 与 QueryWrapper；只有行锁、JSONB 特殊操作、复杂统计等必要场景才直接写 SQL。

客户端从 V0.1 起直接使用 **uni-app x** 工程，不先开发一套独立 Web 客户端再迁移。日常编辑不依赖 HBuilderX，可使用 VS Code / Cursor / Codex；编译、运行、日志和跨端自动化通过 **HBuilderX CLI / `@dcloudio/hbuilderx-cli`** 接入。

AI 开发要求形成闭环：

```text
修改代码
→ CLI 启动前后端
→ Web E2E
→ 读取日志
→ 修复
→ 再次回归
```

Web 是开发期完整 E2E 主平台；微信小程序作为首个跨端 smoke / 回归平台，Android / iOS / HarmonyOS 在进入发行范围后再加入回归矩阵。

LiteFlow 不拥有事件规则，Event Engine 不承担业务流程编排。V0.x 保留 rule/content/balance 版本字段，但不维护多代 Java 规则运行时；开发期重大规则变更允许迁移或使旧 Run 失效。
